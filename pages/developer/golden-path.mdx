# Developer Golden Path

> Docs 0.4 public documentation.

**Requirement:** B-020
**Docs baseline:** 0.4
**Status:** controlled draft / evidence review required

This is the canonical Phase-B developer path for moving from a clean Lariba Cloud workspace to a locally running backend and then through the accepted authentication, source, ingestion, Sentinel, and delivery/recovery workflows.

It composes the accepted B2 developer-environment documentation and B3 product-workflow documentation. It does not replace those documents.

## Safety and scope

This path is for **local development only**.

Do not use production credentials, production databases, production deployment commands, real customer data, or uncommitted web-repository state. Do not commit `.env` values, JWTs, TOTP secrets, recovery codes, source credentials, delivery credentials, or OAuth secrets.

No command in this document was executed by the B4 evidence review itself.

## 1. Enter the backend workspace

From the tracked workspace root:

```bash
cd lariba-cloud
```

Source evidence: `README.md:76`.

**Checkpoint:** commands below that reference `.venv`, Alembic, backend requirements, or backend scripts are run from the canonical backend directory unless a step explicitly says otherwise.

## 2. Install the backend dependencies

The accepted B2 bootstrap evidence establishes dependency installation commands but does **not** establish a repository-authoritative virtual-environment creation or activation command. Therefore this Golden Path does not invent one.

Use the local Python environment intended for Lariba Cloud development, then run the accepted dependency-install sequence:

```bash
python -m pip install -U pip
```

```bash
pip install -r requirements.txt
```

```bash
pip install -r requirements-dev.txt
```

Source evidence: `.github/workflows/ci.yml:74`, `.github/workflows/ci.yml:75`, `.github/workflows/ci.yml:76`.

**Checkpoint:** backend runtime and development dependencies are installed in the selected local Python environment.

If a future documentation tranche standardizes virtual-environment creation, this step should be updated rather than silently introducing an unreviewed convention.

## 3. Configure the local environment

Follow [`environment-configuration.md`](environment-configuration.md).

Supply the required environment-variable names locally. Use placeholders/examples only where already documented. Never commit real secret values.

**Checkpoint:** configuration is sufficient for the intended local backend/database workflow and no secret value has been added to tracked documentation.

## 4. Establish or verify local PostgreSQL

Follow [`postgresql-bootstrap.md`](postgresql-bootstrap.md).

The tracked integration verification path includes:

```bash
bash scripts/postgres-integration-check.sh
```

Source evidence: `lariba-cloud/scripts/full-check.sh:14`.

This script may create/use local integration database state. It is **not** a production command.

**Checkpoint:** local PostgreSQL is available for the backend's documented development workflow.

## 5. Inspect and reconcile the Alembic migration state

Follow [`alembic-workflow.md`](alembic-workflow.md).

Inspect the script graph head:

```bash
.venv/bin/alembic heads
```

Source evidence: `docs/developer/alembic-workflow.md:24`.

For a local development database that is intended to be advanced to the tracked schema head, the repository contains:

```bash
.venv/bin/alembic upgrade head
```

Source evidence: `lariba-cloud/README.md:114`.

This command mutates the configured database schema. Verify that the configured database is the intended **local development** database before running it. Never substitute production connection information.

**Checkpoint:** migration state is consistent with the accepted local-development workflow. If it is not, stop and use the Alembic/troubleshooting documentation; do not stamp or downgrade blindly.

## 6. Start the backend locally

Use the tracked API process command:

```bash
LARIBA_PROCESS_ROLE=api uvicorn src.main:app --host 0.0.0.0 --port 8000
```

Source evidence: `lariba-cloud/README.md:189`.

**Checkpoint:** the local backend process is running and available for the documented workflow surfaces.

## 7. Authenticate

Continue with `../workflows/authentication.md`.

Use only local/development identities and credentials.

**Checkpoint:** the authentication state required by subsequent protected workflow surfaces is established according to the accepted B3 contract.

## 8. Create or select a source

Continue with `../workflows/source-creation.md`.

Preserve source identity, credential, tenant/organisation, and lifecycle boundaries.

**Checkpoint:** a development source exists and its identity/credential handling follows the accepted workflow.

## 9. Ingest an event

Continue with `../workflows/event-ingestion.md`.

Preserve the documented event identity, idempotency, persistence, and source-attribution semantics.

**Checkpoint:** a development event can be traced through the accepted ingestion contract without weakening duplicate/conflict protections.

## 10. Exercise Sentinel

Continue with `../workflows/sentinel.md`.

Follow the accepted rule/evaluation/alert lifecycle rather than inferring behavior from older architecture material.

**Checkpoint:** the development workflow demonstrates the documented Sentinel path and its verification evidence.

## 11. Observe delivery / retry / recovery

Continue with `../workflows/delivery-recovery.md`.

Preserve attempt history, retry/replay, worker, failure, and recovery semantics.

**Checkpoint:** delivery/recovery behavior is inspected through the accepted workflow without using production delivery credentials.

## 12. Verify and troubleshoot

Use [`troubleshooting.md`](troubleshooting.md) for failed checkpoints.

The tracked quick verification command is:

```

Source evidence: `README.md:77`.

```

Source evidence: `README.md:56`.
