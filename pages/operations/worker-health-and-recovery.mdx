# Worker Health and Recovery

Lariba Cloud performs some work asynchronously after an API request has been accepted. Public operational status surfaces can help authorized users understand whether asynchronous processing is healthy, delayed, degraded, or recovering.

This page describes the **developer-visible behavior** of that recovery model. Internal runtime topology, supervision implementation, deployment mechanics, and recovery tooling are not part of the public contract.

## What developers should expect

A temporary runtime recovery can delay asynchronous processing without changing the contract of an already accepted API request.

During recovery:

- accepted requests remain governed by their documented API responses;
- asynchronous work can take longer to complete;
- retry and delivery history remain the authoritative evidence for individual outbound attempts;
- historical failure evidence is preserved rather than rewritten;
- applications should continue to use idempotency and retry-safe integration patterns.

## Health interpretation

Where Lariba Cloud exposes operational health, states may indicate that processing is healthy, degraded, stale, stopped, or failed.

Health is **operational context**, not proof that a specific event, webhook, alert, or downstream action completed successfully.

For an individual operation, use the relevant project-scoped evidence such as event state, delivery history, retry history, or API response data.

## Recovery semantics

Lariba Cloud recovery is designed to preserve evidence across transient runtime failures.

Developers should assume that:

- recovery may create additional retry or delivery evidence;
- original failure records remain available for investigation;
- a recovered runtime does not erase earlier failure state;
- duplicate-safe integrations should use stable idempotency keys where the API supports them.

## Authorization

Operational health and recovery evidence is scoped by Lariba Cloud authorization rules.

A user must not gain access to another organization or project's operational evidence through health or recovery surfaces.

Permissions for mutating actions such as replay, retry, or channel changes are evaluated separately from read-only operational visibility.

## Current boundaries

Operational health does not represent:

- a contractual service-level objective;
- downstream provider availability;
- customer endpoint health;
- successful processing of every individual event;
- a public description of Lariba Cloud's internal runtime architecture.

Use the documented API and project-specific evidence when investigating individual operations.
